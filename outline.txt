# BRILLION — Full-Stack Multiplayer Trivia Website

## 1. Project Objective

Build and deploy a complete, production-ready multiplayer trivia website called **Brillion**, inspired by the gameplay concept of Krillion (krillion.io).

Brillion is a party game in which friends join the same room using their phones, answer seven open-ended trivia questions simultaneously, and compete to provide the rarest valid answers.

One player hosts the game from a computer or other device connected to a television. The main screen displays the question, countdown, player statuses, synchronized answer reveals, points, and standings.

The finished product must be accessible publicly on Render.

**This is a complete application, not a prototype, mockup, or proof of concept.**

Implement the system thoroughly. Do not substitute hardcoded answers, simulated multiplayer, placeholder buttons, fake scoring, or temporary in-memory data for the functionality described below.

Use the actual GitHub repository, Render deployment configuration, database, API, and real-time infrastructure.

If access credentials or external configuration are needed, request them from me rather than disabling the corresponding feature.

## 2. Core Game Rules

Each game consists of exactly seven questions.

Each question:

- Presents an open-ended trivia category.
- Allows each player to submit one valid answer.
- Gives players 25 seconds to answer.
- Rewards rarer valid answers with more points.
- Awards zero points for invalid or missing answers.
- Reveals all players' answers after the timer expires.
- Updates the leaderboard after each round.

Example questions:

- Name a country in Africa.
- Name a Shakespeare play.
- Name a chemical element.
- Name a film directed by Christopher Nolan.
- Name a US president.
- Name an animal native to Australia.
- Name a Nobel Prize in Physics recipient.

Questions must be unambiguous, objectively answerable, and supported by a validated answer database.

### Scoring

Implement the following scoring tiers:

| Tier | Points |
|---|---:|
| Common | 10 |
| Predictably Obscure | 15 |
| Uncommon | 30 |
| Rare | 60 |
| Deep Cut | 85 |
| Brillion | 100 |

The maximum possible game score is 700 points.

A valid answer's point value is predetermined from its rarity classification, not dynamically determined by which players choose it during the current match.

Two players submitting the same answer receive identical points.

Answer speed does not affect scoring.

Each question can have one designated 100-point answer. It should be genuinely interesting and reasonably discoverable, rather than an arbitrary practically unknowable answer.

### Answer Submission

Players can edit their input until they submit or time expires.

Allow submission with Enter or a button.

Once submitted, an answer is locked unless the game explicitly permits correcting a rejected entry before the deadline.

The server must enforce submission deadlines and prevent submitting multiple scored answers per question.

Invalid entries should receive useful feedback while time remains so players can retry, but this must not reveal rarity scores or other accepted answers prematurely.

All answer evaluation is authoritative on the server.

## 4. Multiplayer Synchronization

Use server-authoritative real-time game state.

Implement WebSockets with FastAPI.

Use Redis-compatible storage for shared ephemeral state, distributed synchronization, and event broadcasting.

Use PostgreSQL to persist rooms, players, rounds, and submissions that must survive server restarts.

The architecture must support multiple backend instances without depending on process-local room dictionaries.

### Game State Machine

Implement explicit states:

1. `LOBBY`
2. `QUESTION_PREVIEW`
3. `ANSWERING`
4. `SCORING`
5. `REVEAL`
6. `LEADERBOARD`
7. `FINISHED`

Each state transition must be validated.

The server maintains the canonical state and timestamps.

Clients receive authoritative deadlines and calculate their local countdown displays from synchronized server time.

Do not implement separate independent timers on each client.

Use atomic state transitions, idempotent event handlers, and database constraints to prevent duplicate submissions or repeated scoring.

### Connection Handling

Implement:

- Automatic reconnection with exponential backoff.
- WebSocket ping/pong keepalive.
- Full state resynchronization on reconnect.
- Player session recovery.
- Graceful handling of temporarily disconnected players.
- Host reconnection.
- Host transfer or another explicit recovery mechanism if the host leaves.
- Duplicate-tab handling.
- Room expiration and cleanup.
- Server restart recovery.

A player disconnecting must not stop the game for everyone else.

A player reconnecting must not be allowed to submit after the server-enforced deadline.

### Security

Require appropriate authorization for every host-only action.

A room code alone must not grant administrative privileges.

Use unguessable session tokens, secure storage practices, rate limiting, input validation, and appropriate origin controls.

Do not expose raw WebSocket event handlers that allow clients to alter scores, timers, other players' answers, or game states.

Each question must have:

- Category.
- Difficulty metadata.
- Eligibility criteria.
- Source references.
- Accepted answer set.
- Answer aliases.
- Rarity scores.
- Generation metadata.
- Validation status.
- Review status.
- Version information.

Each answer must have:

- Canonical name.
- Accepted aliases.
- Rarity tier.
- Points.
- Popularity/familiarity evidence.
- Source metadata.
- Validation status.
- Optional interesting fact or explanation.

Example:

```json
{
  "question": "Name a country in Africa",
  "category": "Geography",
  "answers": [
    {
      "canonical": "Egypt",
      "aliases": ["Arab Republic of Egypt"],
      "points": 10,
      "tier": "common"
    },
    {
      "canonical": "Botswana",
      "aliases": ["Republic of Botswana"],
      "points": 60,
      "tier": "rare"
    }
  ]
}
```

These point values are examples, not required scores.

Store normalized answers and aliases efficiently. Add appropriate database indexes.

Use a versioned, immutable published answer bank for each game so that scores remain reproducible if question data is later edited.

## 7. Proper Rarity Scoring

Implement a defensible, reproducible rarity estimation system.

Do not simply ask an LLM to assign arbitrary points and accept those values without calibration.

### Scoring Methodology

Use the strongest available evidence for each question type.

Potential signals include:

- Frequency of mentions in a text corpus.
- Entity familiarity.
- Public popularity metrics.
- Search or pageview statistics, when appropriately licensed and available.
- Dataset-specific popularity measures.
- LLM estimates of recognition likelihood.
- Human-reviewed calibration examples.

Normalize signals separately for different question types.

For instance, movie popularity cannot be measured on exactly the same scale as familiarity with chemical elements.

### Calibration

Develop a rarity calibration process using reviewed reference answers.

Store:

- Raw evidence.
- Familiarity estimate.
- Scoring model version.
- Assigned tier.
- Review status.

Do not assume that dividing the answer database into six equal-sized groups creates a fair rarity system.

The game should measure how likely a typical player is to think of an answer, not merely how rare the underlying object is.

### 100-Point Answers

Select exceptional answers based on:

- Validity.
- Obscurity.
- Interestingness.
- Discoverability.
- Suitability for the category.

Include a short explanation of why the answer is interesting when possible.

### Quality Requirements

The scoring system must be:

- Consistent.
- Deterministic after publication.
- Explainable.
- Auditable.
- Versioned.
- Testable.

Create evaluation fixtures with expected relative rarity orderings.

Flag surprising rankings for review.

## 8. Answer Validation and Spelling Correction

Build robust answer validation.

Support:

- Case insensitivity.
- Leading/trailing whitespace.
- Unicode normalization.
- Common punctuation variations.
- Diacritics.
- Known aliases.
- Common abbreviations.
- Minor spelling mistakes.
- Alternate official names.

Use conservative fuzzy matching.

Avoid automatically mapping an ambiguous guess to an unrelated valid answer.

### Unknown Answer Handling

If a submitted answer is not recognized:

1. Check exact normalized matches.
2. Check aliases.
3. Check conservative fuzzy matches.
4. Check any curated fallback rules.
5. Return an unrecognized result if still unmatched.

Allow players to retry before the timer expires.

For genuinely disputed answers, implement a host-visible review process after the round.

Optionally integrate an asynchronous LLM-assisted adjudication system.

Do not make a live LLM response necessary for the round timer to finish.

Do not award arbitrary or non-reproducible scores to unrecognized answers.

If an answer is accepted following review, assign a documented score, record the ruling, and update the relevant game results atomically.

Preserve an audit trail.

Recalculate affected leaderboards automatically.

## 10. Question Selection

When a host starts a game, the backend should select seven eligible questions.

Selection should:

- Respect selected categories.
- Avoid duplicate questions.
- Avoid near-identical questions in one game.
- Balance subject matter.
- Prefer sufficiently complete, reviewed answer banks.
- Avoid obvious repetition across rematches.
- Preserve the selected question set for the entire game.

Do not generate questions synchronously during game startup.

The question bank should already contain playable content.

Use a reproducible selection process and record the selected question IDs.

If insufficient validated questions exist, show a clear error rather than silently using bad questions.
